# Camera Eye CRM, Attendance Policy, and Alerts QA

This note describes the current implementation on `codex/crm-policy-alerts-finalization-20261010`. All CRM mutations described below are mocked in tests; no production CRM actions, notifications, or deployments were performed.

## Attendance policy and enforcement

Local and cloud attendance workspace pages expose the same policy fields: AUTO/MANUAL, grace, break allowance, required work time, shift start, late grace, max logoff, overtime, absence monitoring/threshold, auto-logout permission, timezone, and notification recipients. Employee overrides inherit unset fields from the shop; response source metadata identifies `EMPLOYEE`/`SHOP`/`SYSTEM` locally and `USER`/`SHOP`/`SYSTEM` in cloud. Local AUTO follows the configured global login gate; MANUAL requires an operator action. Policy saving never flips execution environment flags. Historical activities keep their original policy snapshot.

Threshold validation rejects invalid time/range/weekday/recipient values; prolonged absence threshold is at least 60 minutes. The fixed CRM minimum cannot be configured below the CRM contract. Policy version and updated-at metadata are retained, but effective-from/effective-to scheduling is not implemented by the current API. Cross-midnight reporting is supported; a full automatic shift scheduler and real delivery of notifications remain external acceptance items.

Policy persistence is additive: SQLite `attendance_workspace_policies`; PostgreSQL `attendance_policies.workspace_rules_json` plus additive `alert_operator_state` and `alert_operator_history`. Rollback is application-code rollback only; keep the additive schema and data in place.

## Alerts and access

Local and cloud Alerts use the same browser workspace and scoped APIs: `GET …/alerts/workspace`, `GET …/alerts/export`, `GET …/alerts/{id}`, and `POST …/alerts/{id}/action`. Local records remain shop-scoped and local evidence resolution is confined to the configured evidence root; cloud queries and media require portal session plus tenant/shop scope. Only owner/admin/superadmin/manager can acknowledge/resolve; operator may read. A state change requires an expected prior state, reason, and request ID; a tenant/shop/alert advisory lock and journal make transitions auditable. Original detector records are not modified. Unknown incidents retain no employee identity. The UI reports unavailable evidence rather than exposing filesystem paths.

## QA record and reproducible isolated commands

Focused pytest coverage is in `tests/test_alerts_workspace.py`, `tests/test_attendance_workspace.py`, `tests/test_postgres_attendance_workspace.py`, `tests/test_policy_resolution.py`, and the existing CRM/bridge/notification regression files. On 2026-10-10 the 14-file targeted regression run completed **170 passed, 4 skipped, 0 failed**; the skips were opt-in browser cases. A separate real-Chrome run completed **4 passed**: local/cloud attendance policy and override pages, local/cloud alerts, evidence preview, acknowledgment/resolution, and mobile width. Browser data was synthetic and services bound to loopback only. Screenshots are written to `artifacts/attendance-alerts-browser/` and `artifacts/attendance-workspace-browser/` (untracked QA artifacts are not included in the source commit).

Start the isolated PostgreSQL fixture with `docker compose -p camera-eye-personnel-tests -f compose.postgres-test.local.yml up -d postgres-test`, then set:

```powershell
$env:SNAPKEY_TEST_DATABASE_URL='postgresql+psycopg://camera_eye_test:camera-eye-test-only@127.0.0.1:55432/camera_eye_test'
$env:SNAPKEY_REQUIRE_POSTGRES_TESTS='1'
$env:CAMERA_EYE_WORKSPACE_BROWSER='1'
python -m pytest -q tests/test_alerts_workspace.py tests/test_attendance_workspace.py tests/test_postgres_attendance_workspace.py tests/test_policy_resolution.py
```

The fixture rejects any database other than loopback `camera_eye_test` and creates/drops a unique test schema. If tests are run without `CAMERA_EYE_WORKSPACE_BROWSER=1`, Chrome checks are skipped. For a code rollback after a future approved deployment, revert the release commit (`git revert <release-sha>`) and redeploy the prior known-good cloud/edge artifacts through the approved release pipeline; keep additive tables and data in place. Do not drop schemas or delete generated/attendance records. No production command is part of QA.

## Remaining release gates

Before release, run the full relevant suite in CI and verify CRM Face Login's identity fields, break response bodies, and success status against CRM staging. Confirm scoped roster service credentials if monthly roster is needed. Perform a staging employee/token test and reconcile one successful and one uncertain CRM mutation. Verify SMTP and WhatsApp with mocks and approved staging endpoints. Review generated desktop/mobile screenshots. Keep `SNAPKEY_CRM_AUTO_LOGIN_ENABLED` and `SNAPKEY_CRM_AUTO_LOGOUT_ENABLED` unchanged until the corresponding staging/production authorization; neither was enabled here.
